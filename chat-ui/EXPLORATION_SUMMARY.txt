EXECUTIVE SUMMARY
=================

The claude-agent-sdk-rust SDK provides two main APIs:

1. SIMPLE QUERY API (query function)
   - One-shot, stateless queries
   - Returns stream of messages
   - No connection management
   - Best for: CLI tools, batch processing

2. INTERACTIVE CLIENT API (ClaudeSDKClient)
   - Stateful conversations
   - Bidirectional communication
   - Lock-free concurrent operations
   - Best for: Chat UI, REPL-like interfaces

KEY INSIGHTS
============

1. DUAL ENTRY POINTS
   - query() - Simple unidirectional stream
   - ClaudeSDKClient - Complex bidirectional management
   - Choose based on interaction pattern

2. BACKGROUND TASKS (6 total)
   - Message Reader - Reads CLI output continuously
   - Control Writer - Writes commands to CLI
   - Hook Handler - Processes hook events (if configured)
   - Hook Callback Handler - Routes CLI callbacks (if configured)
   - Permission Handler - Checks permissions (if configured)
   - MCP Message Handler - Processes MCP requests (if configured)
   - All spawned automatically on client creation
   - No manual task management needed

3. LOCK-FREE CONCURRENCY
   - Reader task acquires lock ONCE to get receiver
   - Releases immediately, then processes messages
   - Writer task locks briefly for each write
   - Result: NO CONTENTION between read and write
   - Safe concurrent send/receive

4. MESSAGE FLOW
   - User messages flow through unbounded channels
   - Each message type (User, Assistant, Result, etc.)
   - Control messages filtered out at reader task
   - Only application messages delivered to code

5. CLI INTEGRATION
   - Wraps Claude Code CLI process
   - Automatic mode selection (streaming vs print)
   - Configuration via CLI arguments
   - Security: env var filtering, flag allowlist, buffer limits

6. PROTOCOL LAYERS
   - Transport Layer - CLI subprocess management
   - Message Layer - JSON parsing and serialization
   - Control Protocol - Init handshake, interrupts
   - Hook System - Event interception
   - Permission System - Tool access control
   - MCP System - Custom tool integration

7. ERROR HANDLING
   - Rich error types with context
   - Includes exit codes and stderr
   - Raw JSON data included in parse errors
   - Helpful messages for missing CLI

8. CONFIGURATION
   - Builder pattern for options
   - Type-safe newtypes (SessionId, ToolName, RequestId)
   - Sensible defaults
   - Optional features (hooks, permissions, MCP)

CRITICAL IMPLEMENTATION DETAILS
===============================

1. Transport Layer
   - Subprocess-based (CLI wrapping)
   - Streams JSON messages
   - One message per line (newline-separated)
   - Message reading happens in background task

2. Message Types
   - User, Assistant, System, Result, StreamEvent
   - Result signals conversation end
   - System/StreamEvent are informational
   - Control messages filtered out

3. Async Pattern
   - All I/O is tokio-based
   - Channels for task communication
   - Mutexes for shared state protection
   - Arc<Mutex<T>> for ref-counted locks

4. Hook System (Optional)
   - Intercepts tool usage
   - Pattern matching on tool names
   - Callback IDs generated and tracked
   - Can block actions or add context

5. Permission System (Optional)
   - Checks tool access
   - Supports allow/deny lists
   - Custom callback logic
   - Can modify tool input

6. MCP System (Optional)
   - In-process tool implementation
   - JSONRPC protocol
   - No subprocess overhead
   - Direct async function calls

GOTCHAS AND EDGE CASES
=======================

1. Control messages don't appear in message stream
   - control_response and control_request filtered
   - Only User/Assistant/Result/System/StreamEvent reach app

2. Hook callback IDs must match initialization
   - Format: hook_0, hook_1, etc.
   - Used to route CLI callbacks

3. Streaming mode activation
   - Auto-enabled for ClaudeSDKClient
   - Auto-enabled if hooks/permissions/MCP configured
   - Otherwise uses print mode for efficiency

4. Permission defaults
   - No allowed_tools = all allowed
   - With allowed_tools = only those allowed
   - Disallowed_tools checked first (deny wins)

5. Reader lock pattern
   - Lock acquired once, released immediately
   - Safe for concurrent operations
   - No contention with writer

6. Channel closures
   - Tasks exit when channels drop
   - Resources cleaned via Arc drops
   - No manual cancellation needed

7. Interrupt support
   - Sent correctly by SDK
   - CLI may not process in all versions
   - Architecture supports it
